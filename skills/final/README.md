# Elixir / Phoenix / Ash skills

A distilled skillset for Claude Code, built from sets `1/`, `2/` and `3/` and from selected files of `oliver-kriska/claude-elixir-phoenix`. Checked against Ash 3.37, AshPostgres 2.15, AshPhoenix 2.3, Phoenix 1.8.16, LiveView 1.2.13 and Elixir 1.20 (October 2026).

This README is for you. Claude never loads it.

## The skills

| Skill | Loaded | SKILL.md | References |

| `building-with-ash` | automatically, on Ash work | ~70 lines | actions, querying, policies, relationships, postgres, forms, testing, authentication, oban |
| `building-phoenix-liveview` | automatically, on web-layer work | ~60 lines | liveview, ecto-forms, js-interop, testing |

The standing cost is three descriptions, roughly 200 tokens. A SKILL.md body loads only when its skill triggers, and a reference file loads only when the task needs it.

## Install

```bash
# personal: available in every project
mkdir -p ~/.claude/skills
ln -s "$PWD"/final/{building-with-ash,building-phoenix-liveview,writing-elixir,auditing-phoenix-ash} ~/.claude/skills/

# or per project (commit it to share)
cp -r final/building-* final/writing-elixir final/auditing-phoenix-ash <project>/.claude/skills/
```

Symlinks mean that `git pull` here updates every project.

## Design decisions

1. **Point at version-exact docs instead of copying them.** Sets 1–3 are `usage_rules` snapshots of the same upstream files, about 95% identical, with set 3 the newest. They go stale on every release. Ash and Phoenix ship those same rules inside the package (`deps/<pkg>/usage-rules/*.md`), and those always match the installed version. So each skill keeps only the rules agents get wrong plus working patterns, and its "Source of truth" section sends Claude to the deps, `mix usage_rules.search_docs`, Tidewave and hexdocs for everything else.
2. **Cut what Claude already knows.** Dropped: generic explanations ("Ash is an opinionated framework…"), the 60-line lists of mix tasks (`mix help` has them), duplicated examples, and "Iron Law" capitals and invented memory benchmarks.
3. **Progressive disclosure, as Anthropic's guidance recommends.** SKILL.md stays well under 500 lines, references are one level deep, and files over 100 lines start with a table of contents. Descriptions are in the third person and say *what* the skill does and *when* to use it.
4. **Names that don't collide.** In Claude Code a personal skill overrides a project skill with the same name. `usage_rules` generates `ash-framework`, `phoenix-framework` and `use-<pkg>` skills inside projects, so these skills use different (gerund) names and both can coexist.
5. **Procedures are user-invoked.** The audit has `disable-model-invocation: true`, so it costs nothing until you run it.
6. **Version-gated notes.** Newer features are marked "(3.36+)", "(1.1+)" and so on, instead of "as of date X".

## Bugs found in the source material (fixed here)

1. **Stream prepend.** Sets 1–3, and the `AGENTS.md` generated by Phoenix ≤ 1.8.15, say to prepend with `at: -1`. That *appends*; prepending is `at: 0`. Phoenix `main` has fixed it, but projects generated earlier still carry the bug in `AGENTS.md`.
2. **`check_constraint` signature.** The AshPostgres usage-rules omit the constraint name. The DSL is `check_constraint :attr, "name", check: ..., message: ...`.
3. **`custom_statements` syntax.** The usage-rules use `statement "SQL"`. The DSL is `statement :name do up "..."; down "..." end`, and Postgres extensions belong in the repo's `installed_extensions/0`.
4. **AshPhoenix `forms` example.** It says the result is called as `register_with_password(email, …)`. The generated function is `form_to_register_with_password(email, …)`.
5. **`after_transaction` example in actions.md.** The error branch uses an unbound `result` variable.
6. **claude-elixir.**
   - "Execution-level actor bypasses row-level policies" gives the wrong reason. The real one: changes, validations and preparations run while the changeset is built, so they never see the actor.
   - Its "policy checks `use Ash.Policy.Check`" should be `SimpleCheck`/`FilterCheck`.
   - "Use temporary_assigns for flash messages" is wrong.
   - `[item | list] |> Enum.reverse()` doesn't replace `list ++ [item]`.

## Recommended per-project setup

- **`phx.new` 1.8 writes `AGENTS.md`.** If your Claude Code setup doesn't pick it up, put `@AGENTS.md` in `CLAUDE.md`. Change its stream line to `at: 0`.
- **Add `mix ash.codegen --check`** to the `precommit` alias in Ash projects.
- **Optional:** add `tidewave` (version-exact docs and evaluation inside the running app) and `usage_rules`, which gives you `mix usage_rules.search_docs`. If you also let `usage_rules` generate project skills, keep them; they complement these.

## Maintenance and testing

- When a major version changes (Ash 4, LiveView 2, AshAuthentication 5 final), re-check the "Rules" sections and the version notes. The "Source of truth" pointers keep everything else current on their own.
- To check that the skills trigger and help, run these prompts in a scratch project with and without the skills and compare:
  1. "Add a `publish` action to Post that sets `published_at` and only lets the author do it, and expose it in the LiveView." Expect a named atomic action, a policy using `forbid_unless`/`relates_to_actor_via`, a code interface, codegen, and a scoped `handle_event`.
  2. "The post list should show new posts at the top in real time." Expect `Ash.Notifier.PubSub`, `connected?` subscribe, and `stream_insert(..., at: 0)`.
  3. "This create form does nothing on submit." Expect it to check the `{:error, form}` branch and `AshPhoenix.Form.raw_errors(form, for_path: :all)` before touching the UI.
